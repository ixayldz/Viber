# External Privacy Metadata and Native Fence Quota Design

**Status:** design and audit only; no runtime closure claimed.

**Source reviewed:** repository `HEAD 1765582` (`feat: charge support, delivery preview, and GC records to the shared physical quota`), compared with the requirements in `prd.md`, `docs/MANAGED_WRITER_INVENTORY.md`, and `docs/KEYLESS_DELIVERY_PLAN.md`.

**Scope:** the remaining shared physical quota work for external privacy metadata and native process/fence identities. Restore-stage and evaluator-owner writers remain separate inventory items.

## Finding

The shared `resource.Ledger` is already used by several payload writers, but a safe runtime patch for privacy journal/checkpoint/migration files cannot be made by adding a `Reserve` call to `appendPrivacy`. First-owner privacy authority creation publishes metadata before the ledger exists, and the current ledger API models one-shot directory snapshots rather than deltas to a shared append/update tree. A partial hookup would leave bootstrap, owner catalog, checkpoint retirement, or recovery uncharged while appearing to close the writer.

The native runner has a separate remaining gap. It correctly reports engine metadata bytes as unknown, but its 4,096 limit is a per-instance count of containers currently returned by Docker. Normal `Run` cleanup removes those containers, so repeated runs do not accumulate against the limit; separate instances and separate brokers also do not share an atomic identity budget. Existing task cleanup receipts preserve some fencing evidence, but they are not an engine-wide lifetime ledger.

## Bootstrap and self-accounting boundary

The first authority has a circular authority problem: its shared physical ledger is stored inside the external privacy authority directory, but that ledger is supposed to authorize writes to the same directory. The physical root identity is only available after directory creation, while the current owner-store CAS accepts the complete identity only after creation. The ledger's own SQLite pages/WAL/SHM, anchor and lock cannot safely reserve themselves by recursively inserting another row into the same ledger. The separate external `control.reserve` file and the ledger's bounded metadata also consume real disk, even though neither is currently charged as an ordinary writer.

Break the cycle with a durable, bounded **owner-store bootstrap reservation** that exists before `mkdir`:

1. In one owner-store transaction, write a pending bootstrap descriptor containing authority ID, canonical prospective path, existing parent and volume identities, owner-store/instance and generation, request digest, fixed byte/entry upper bounds, and a bootstrap schema version. This is a bootstrap control reservation, not a normal shared-ledger record.
2. Create only that reserved path. CAS-bind the measured physical root to the pending descriptor. On mismatch, foreign contents, or changed volume, stop admission and retain the reservation as unknown.
3. Publish authority genesis, create/anchor the shared ledger, create or verify the bounded control reserve, and inventory every pre-ledger file and directory. The ledger must not be considered current until the inventory has been imported and a current anchor/pin binds its identity.
4. Transfer the bootstrap charge to imported ledger allocations through an idempotent `PENDING → IMPORTING → BOUND → RELEASED` protocol. On crash, retry the same descriptor and digest; never clear the owner-store charge before the imported receipt and owner pin are durable. Duplicate charge during recovery is acceptable; a charge gap is not.
5. A legacy backup that references a non-empty authority but has no current ledger pin/anchor may enter explicit migration/recovery only. It must not open a fresh empty ledger and admit ordinary writes. A current owner pin whose ledger is missing or replaced remains stale/fail-closed.

Reserve a finite bootstrap/allocator-overhead class separately from ordinary payload so the ledger can record its own bounded operation without recursion. Either account the existing privacy control reserve and ledger metadata as that fixed overhead, or consolidate the reserves under one measured implementation. Do not silently exclude both from the quota, and do not charge all ordinary journal traffic to protected emergency capacity. Keep ordinary privacy metadata in its bounded work class; reserve protected control capacity for delete intent and bounded recovery/fence records. The exact reserve sizes and ledger-page ceiling must be reconciled with `resource.DefaultLimits` before implementation.

## Shared-tree mutation contract

`resource.Reserve/Begin/Commit` in [quota.go](../internal/resource/quota.go) currently pins a target directory, reserves an upper bound, and settles one final inventory. `targetVolume` (2223 onward) rejects an existing non-directory target; overlapping exact directory reservations are intentionally rejected. This works well for one-shot bundle writers. It does not directly model a sequence of records appended below one shared `records/` directory, replaceable checkpoint anchors, or per-operation changes to one retained metadata tree.

Add a bounded mutable-managed-tree primitive before wiring these writers. It should pin one exact existing metadata root and current inventory digest, atomically reserve the **additional** upper bytes/entries for one revision, and keep the old retained charge plus the new outstanding upper charge visible while writing. The root's privacy lock serializes sequence/anchor changes; define one lock order (`privacy registry → quota ledger`) and ensure no caller can hold the quota lock while acquiring the registry lock. Admission binds authority ID, physical root, target volume, owner instance/store, writer kind, generation, request digest and class.

The writer publishes by temp/write/sync/rename as it does today, then measures the exact full post-write inventory and settles the revision. A process death leaves the revision `WRITING`; reopen measures under the same root and current authority, then either adopts the exact result or retains the upper bound/UNKNOWN charge. Do not lower retained charge based on logical file length, a renamed path, an absent name, or a free-space observation. Release old records/checkpoints only through exact unlink identity/digest/allocated-size and volume-free receipts, using the existing `ReleaseFile`/`FREE_PENDING` pattern. Quota reservation/catalog rows belong in the bounded quota ledger, not in the 1,536 ordinary privacy JSON-record slots.

Use this primitive for:

- `appendPrivacy`: reserve the record's write upper before temp creation and sequence publication; retain ordinary/control classification and the existing 1,536/512 slot split.
- owner scope/catalog creation in `attachPrivacy`: include the owner lock/scope entry and any directory creation before publishing it.
- `CheckpointPrivacyMetadata`: reserve checkpoint data, intent, next/current anchor and history objects as one recoverable revision; carry the same reservation through owner-pin transition and historical retirement.
- migration: before publishing migration intent or mutating the DB, reserve the bounded DB/WAL/SHM plus sidecar/write-temp upper on the correct physical volume. Include a legacy/bootstrap path when the existing owner has no shared ledger. The existing `pages * pageSize * 3 + 32 MiB` free-space check can remain a preflight guard but cannot be represented as quota closure.

Import initial retained metadata in separate exact, bounded inventories (for example journal records, checkpoint subtree and owner catalog) or restructure under a managed subtree. Do not import the entire authority root as one ordinary payload tree: that includes allocator files, control reserve and mutable lock/control files and makes future ledger writes recursively change the measured root. Whichever inventory boundaries are chosen must be versioned and anchored, account directory entries, and reject foreign or unmeasurable members.

## Native identity ledger

Keep engine physical storage and identity admission as separate measurements. `Capacity.PhysicalBytesKnown == false` is correct when the Docker engine does not expose a validated physical measurement. Do not translate that state into a zero-byte inventory or free capacity.

Add a durable engine-scoped identity ledger keyed by the verified `EngineID`, shared across runtime instances and broker processes. Before create, atomically reserve a lifetime identity slot and persist the full request binding: engine, instance, task/parent, writer/lease, generation, capsule and invocation digests, unique engine name, and request digest. States should distinguish at least `RESERVED`, `CREATE_UNKNOWN`, `ACTIVE`, `REMOVED`, `FENCE_HELD`, and `RELEASED`. A lost create acknowledgement remains charged until exact-name/full-ID inspection and reconciliation. `Reconcile` must persist its fence identity before claiming completion; unstarted fences consume capacity. Store the exact removed IDs and their lineage for replay and diagnostics.

Count the configured lifetime budget over durable admitted identities, not just `docker ps` output and not one isolated instance. Removing a normal container frees engine objects but does not erase its identity receipt. Release a fence/slot only with a durable capability receipt proving that no delayed old create/start can succeed; if the supported engine cannot prove that, keep the charge. Report identity slots and unknown engine bytes separately in status. This ledger needs an engine-global authority outside per-project privacy roots; otherwise one project or restored backup can reset the count. Its own bounded database/bootstrap overhead needs an explicit fixed control budget, with no fabricated engine byte measurement.

The current Docker `d.mu` serializes one `Docker` object only. The new identity admission needs a durable cross-process CAS/lock and must re-read capacity at reservation time. Engine ID changes or endpoint changes invalidate the old ledger binding; an unknown engine identity blocks admission rather than creating a new empty ledger.

## Acceptance backlog; none is implied by this design

Run these gates against the exact source revision that implements the design, with fixture, subprocess, filesystem-native and engine-native results reported separately:

1. **Bootstrap fault points:** death before the owner CAS, after pending CAS, after directory create, after physical-root CAS, after genesis, during ledger DB/anchor creation, after import, after owner pin, and before bootstrap-charge release. Same-path restart must complete the exact pending allocation; changed parent/root/volume, foreign files, duplicate genesis, missing/replaced ledger, and stale backup must stop admission.
2. **Concurrent bootstrap and lock order:** two owners restoring the same authority concurrently; one winner/current anchor; no duplicate owner/root/ledger adoption. Race append/checkpoint/migration against payload admission and reserve replenishment; assert one documented lock order and bounded cancellation without deadlock.
3. **Physical exhaustion:** separate ordinary/control exhaustion, real ENOSPC on each metadata target volume, low-water behavior, actual control reserve publication/rearm, byte/entry overflow, allocation/receipt failure, duplicate retry and crash before/after each temp, sync, rename, anchor, owner pin and release receipt. Reopen with exact inventory must replay the same journal/checkpoint state.
4. **Legacy import/migration:** old backup with records and checkpoints but no quota pin/ledger; exact inventory import above quota remains charged and blocks new admission. Stale checkpoint/backup cannot restore an older privacy journal or ledger. Schema migration must admit its DB/WAL/SHM and sidecar upper before first write; crash recovery reuses the same reservation and command ID.
5. **Metadata lifecycle:** append, owner-scope publication, checkpoint, anchor rotation, retention/prune, duplicate command and retry all preserve exact measured entries/bytes. No quota charge is released without inode/root/hash/allocated-byte and volume-free proof. The existing semantic slot limits must still deny before publication, and quota reservation rows must not consume privacy journal slots.
6. **Native lifetime:** actual pinned engine test for simultaneous brokers at the last slot, multiple runtime instances, repeated successful create/rm beyond the configured lifetime budget, response loss, owner crash, same-engine process restart, fence persistence, late create/start rejection, capacity observation and any release case. Engine bytes remain UNKNOWN unless that engine/profile has an independently validated physical measurement.

Until these design decisions and exact-revision gates are implemented, the honest status is: **shared quota core and several one-shot writers are present; external privacy metadata/checkpoint/migration quota, ledger bootstrap/import, and engine-global durable identity lifetime charging remain open.**
