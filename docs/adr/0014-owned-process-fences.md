# ADR 0014 — Durable process leases and engine name fences

Date: 2026-10-09. Status: IMPLEMENTED engineering slice; full PRD backend acceptance remains open.

A native check must publish its process lease and every allowed subject capsule before contacting Docker. The physical store has an opaque random instance ID bound to the filesystem directory identity. It is excluded from backup: an explicit fresh restore receives a new identity. Copying the identity into another directory or losing it after owned history is retained fails closed.

Each capsule binds instance/task/operation hashes, lease ID, generation, policy epoch, spec version, monotonic clock domain/deadline, baseline/candidate/check phase, ordinal, pinned profile, exact invocation including stdin, source mount digest and candidate digest. Containers have deterministic capsule names and protected engine labels. The subject cannot access the engine socket. No prompt, oracle, credential or raw task ID enters these labels. Each dispatch checks its live monotonic lease again; persisted clock coordinates cannot authorize a new process after restart.

An abrupt owner death can leave a process or an in-flight create request. Merely finding no containers is insufficient. Explicit `reconcile-native-risk` requires the original physical store, a newer generation, a retained UNKNOWN native reservation and a bound user command. The broker inspects the complete bounded lease group before any mutation, validates exact full engine identities/profile/mount/invocation, removes matching subjects and holds an unstarted fence container under every admitted subject name. A delayed old create cannot acquire the name; an old start cannot use the removed full container ID. A race or lost fence-create reply is reconciled by exact name and identity with a bounded retry. An unexpected same-label process, started/altered fence or missing engine proof prevents settlement.

Fence containers never execute an entrypoint and use the same pinned offline non-root bounded profile. They must remain in the engine while delayed requests from the old owner could still exist. There is deliberately no automatic fence pruning or blanket Docker cleanup. Host engine administration, deletion/pruning of fences or filesystem identity behavior outside the tested backend are not untrusted-subject capabilities. Full rootless/namespace/host child lifetime/backend matrices and a supported safe fence-retention policy remain separate work.

Successful cleanup retains a source-bound receipt, charges the complete native CPU/disk/time allocation, releases child risk and appends an error tool reply at the existing cursor. No lost stdout, candidate mutation, inference response, PASS, quality upgrade or fulfilled obligation is accepted. It may exhaust the task budget. Partial/altered proof leaves the UNKNOWN intent/reservation intact and retains an incomplete receipt. Repeating a command ID does not repeat cleanup; an incomplete command needs a fresh cursor and new command ID. Historical proof and its original document remain GC/backup roots. Already-settled tool replies do not pin otherwise-unreachable CAS objects.

`runtime-info` is read-only and exposes eligibility, hashes, subject counts, receipt references and a command template. The CLI and secure owner RPC share the implementation; TUI `/runtime` shows it. An owner in the old generation cannot reconcile itself. Legacy unowned intents and restored copies cannot use this path to clear risk.

Evidence: pure adversarial tests cover foreign/altered groups before any removal, delayed create, lost acknowledgement, expired/same-generation leases, failed-command dedup, full accounting, no quality grant, clone/restore/missing identity and retained proof validation. Actual Docker tests cover a running child orphan, removal/full-ID fencing, late create/start rejection, and abrupt death of a real agent subprocess. Native Windows and pinned Linux race results are recorded in VALIDATION; compile-only macOS is not native acceptance.
